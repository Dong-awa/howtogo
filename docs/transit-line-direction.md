# 公共交通线路的方向性

一条线路有两种可能的运行方式，本模组现在把它们区分开：

| 方向 | 含义 | 寻路 |
|---|---|---|
| **双向**（默认） | 两个方向都有车 | 站点列表里相邻的两站之间，两个方向都可以乘车 |
| **单向** | 只有按列表顺序运行的车 | 只能从列表中靠前的站乘到靠后的站，反向没有行程 |

站点列表的顺序**就是**方向，没有第二个「往哪边单行」开关：想让线路反过来跑，把站点顺序调过来即可。

## 线路配置界面

线路配置界面在「颜色」下面多一行「方向」，两枚 chip：`双向` / `单向`。

- 点一下即刻写进线路并保存（线路文件的自动保存与其它编辑一样，3 秒防抖）。
- MTR 导入的线路**只读**显示识别到的方向（见下），点不动；要改就「复制为我的」，方向会一起复制。
- 线路列表里单向线路带一个「单向」标记，不必点开每条线路才知道哪条受限。
- 新建线路默认双向，旧线路文件没有方向字段的也按双向读。

## 文件

线路文件里多一个可选字段，与颜色同一层：

```json
{ "id": "...", "name": "环线", "kind": "RAIL", "direction": "one_way", "stops": [ ... ] }
```

- 写入时**总是**写 `"direction"`（`"two_way"` 或 `"one_way"`），文件自己说明线路是什么，而不是让读取方从「没写」去推断。
- 读取时缺字段、或字段是这一版不认识的词，一律读成**双向**——这是唯一不会凭空造出一条限制的答案（与道路的 `direction` 同一规则）。
- 格式版本 `version` 不变：这个字段是可选的，旧版本读到会忽略，新版本读到旧文件也不会出错。

## 寻路

单向线路在**构图时**就不生成回程边，而不是先搜出反方向的行程再判它非法。

- 因此从线路末尾往开头乘车不会出现在任何一趟行程里，`没有行程` 是诚实的答案，而不是「有，但被丢掉了」。
- 线路中段上车照常可以：从第 2 站乘到第 3 站是这条服务会做的事，规则针对的是「两站之间的那一段」，不是整条线路。
- 换乘与「公交混步行」不受影响：换乘是站与站之间的一小段步行，步行本身没有方向限制。
- 导航里的「开往 X」照旧取该次乘车方向上线路的终点站；单向线路只可能开往列表最后一个站。

## MTR 的识别

MTR 自己没有「单向」这个词，它有线路的**环线状态**（`CircularState`）：`NONE` / `CLOCKWISE` / `ANTICLOCKWISE`。
环线是一条绕圈单向运行的服务，因此：

- `NONE` → 双向
- `CLOCKWISE` / `ANTICLOCKWISE` → 单向

判定在「读数 → 本模组线路」的那一次转换里做（`MtrTransit.buildLines`），所以三条读数路径都覆盖：
4.x 客户端窗口（`SimplifiedRoute`）、4.x 单人/局域网整图与服务端读数（`Route`）、MTR Map Overlay 的快照
（`MapRoute.circular`）。MTR 3.x 的读数会尝试读同名状态，**但本机没有 3.x 的 jar 可核对**，读不到时按双向处理。

MTR 的读数永远是只读的：方向识别结果只显示，「复制为我的」之后才是玩家的线路、才可以改。

## 地图

- 两张地图与 HUD **默认不标注方向**：地图是看「线路在哪、在哪换乘」的，箭头会把线画花。
- 唯一例外是**开启编辑模式的 Xaero 世界地图**：沿单向线路每 64 格画一个小箭头，箭头朝乘车方向，线色上仍可辨认；
  双向线路不画（它没有单一方向，画任何一个都会是错的）。关闭编辑模式箭头即消失。
- 本模组自绘的地图（K 主界面、目的地选择小地图、导航 HUD 小地图、手机页）与 Xaero 小地图叠加层都不画。

## 为什么不这样做

- **为什么不复用道路的 `RoadDirection`**：道路的单行是每一段路自己的属性，有两个方向，取决于从哪一端进入；
  而线路只有一个顺序、没有自己的几何。用道路的三态描述线路，会让一条线路能在「半条自己身上」反向运行。
- **为什么不在搜索结果上事后过滤**：事后过滤会让搜索先走一条服务不允许的路，再把走出来的答案判为无效，
  于是它会错过真正成立的行程——「没有公交行程」就从答案变成一种丢弃。
- **为什么不在双方向时画两个箭头**：双向线路是「两个方向都有车」，箭头只会让读者以为那是两条不同线路的走向；
  方向是单向线路才有的信息。
