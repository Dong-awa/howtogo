# MTR 版本支持

问道的 MTR 集成是**反射只读**的：不引用任何 MTR 类，MTR 没装、换了版本、换成分支，都不会让问道起不来，
只会让这份读数不可用。MTR 自己的数据模型换过一次大版本，所以读取器有两套，装的是哪套由类名决定。

| MTR 数据模型 | 版本 | 读取器 | 能读到的 |
|---|---|---|---|
| 4.x | 4.0.4 及以上 | `MtrClientData` / `MtrWholeMap` / `MtrServerData` | 客户端窗口、单人/局域网的整张路网、服务端同步（1.20.6–1.21.1 节点） |
| 3.x | 3.x 全线，含 YMTR 分支 | `Mtr3Data` | 客户端窗口、单人/局域网的整张路网（含全量轨道） |

## 两套模型差在哪

4.x 把数据搬到了与加载器无关的模拟核心里：客户端拿 `SimplifiedRoute` 与 `RailWrapper`，服务端每维度一个
`Simulator`，元素是 getter 访问的。3.x 的数据在客户端与世界的存档数据里：`ClientData` 的静态集合、
`RailwayData`，元素是 public 字段、没有 getter，轨道按两端方块存在 map 里、**没有 id**。

读取器只在这些地方不同，读出来的东西是同一种：车站、站台、线路、轨道，再交给本模组的转换，地图、目的地
列表与寻路不区分读数来自哪套模型。

## 线路的方向

MTR 的线路有自己的**环线状态**（`CircularState`：`NONE` / `CLOCKWISE` / `ANTICLOCKWISE`）。环线是一条绕圈
单向运行的服务，所以导入时 `NONE` 成双向线路、另外两个成单向；判定只在「读数 → 线路」的那一次转换里做，
三条读数都覆盖（4.x 窗口读 `SimplifiedRoute`、4.x 整图与服务端读 `Route`、Overlay 快照读 `MapRoute.circular`）。
MTR 3.x 会尝试同名状态，但没有 3.x 的 jar 可核对，读不到时按双向处理。规则与界面见
[transit-line-direction.md](transit-line-direction.md)。

## MTR Map Overlay 的版本

Overlay 的快照是第三条读数：在别人的服务器上、既没有本地模拟也没有本模组的服务端同步时，它是唯一能看到
整张路网的一条。它在 1.5.2 把类包名从 `com.lx862.mtrmap` 改成了 `io.github.teamcreating.mtrmap`，字段与方法
一个没动，所以读取器两套名字都认、按新名优先，1.5.1 及更早也照旧能读。绑到的是哪一套写在日志里：

```
[HowToGo] MTR Map Overlay's fetched railway is readable (io.github.teamcreating.mtrmap.mapdata.MapDataCache)
```

1.6.0 起 `MapTrack.points` 的每个点是「X、Z、真实世界 Y」三段，问道读到 Y 就直接用它当这条轨道的高度；
旧快照的平面点只有 X、Z，仍按「最近的车站/站台 48 格内」估高，都没有就落在 64 层。快照里没有交通类型
（Overlay 只采样 TRAIN 轨道），所以这份读数一律按铁路处理。

两套名字都绑不上时，日志里是 `MTR Map Overlay's fetched railway is unavailable (...)`，地图上就没有它抓取的
车站与线路。回归 `tools/routing-harness` 在「给了 Overlay 的 jar 却绑不上」时直接判失败，不再当成没装跳过；
给了 jar 时还会用它的 `DimensionData`/`MapRoute`/`MapTrack`/`MapLandmark` 造一份快照真跑一遍转换，见下文。

## 3.x 上几个必须知道的事实

- **站台没有车站字段**。3.x 的 `SavedRailBase` 不像 4.x 那样带 `area`，唯一的精确联系是
  `DataCache.platformIdToStation`；这张表没有时按「站台落在哪个车站矩形里」兜底（重叠取最小矩形）。
- **车站区域没有高度**。`AreaBase.getCenter()` 的 y 恒为 0，所以车站高度取它所有站台的平均高度，
  目的地标记才不会画在地底。
- **轨道 id 是编的**。3.x 的轨道没有 id，而客户端的合并与服务端同步都按 id 对轨道；现在用
  「两端方块坐标（与方向无关）+ 交通类型」拼 `m3:` 开头的 id，跨读数、跨窗口/服务端副本都稳定。
- **3.x 没有「这条线走哪几条轨道」**。4.x 的服务端读数也没有；线路的轨道照旧由「按站序在轨道上规划」
  得到，见 `MtrLineTracks`。
- **整图读数带全量轨道**。MTR 3.x 只把玩家附近的轨道发给客户端，只读窗口就会「轨道断断续续、部分丢失」；
  单人/局域网主机进程里有整维度的 `RailwayData`，所以整图读数从 `getRailsMap()`（没有 getter 的版本退回
  私有 `rails` 字段）把轨道全读出来，仍用 `m3:` id 与窗口读数去重合并——窗口的那份先到先留（它有真实高度
  与交通类型），整图补的是窗口没有的那部分。采样几何是整个读数里最贵的一步，所以转换结果按轨道 map 的
  内容签名缓存：签名不变（网络没动）就整份复用，变了才重新采样；缓存里只有本模组自己的记录，不留 MTR 对象。
- **3.x 服务端同步要补传输层**。`MtrServerSync` 的网络包只在 1.20.6–1.21.1 编译，而 MTR 3.x 只存在
  1.20.1，所以 1.20.1 上的 3.x 只有客户端窗口与单人/局域网整图两条读数；玩家在别人的服务器上时，
  读到的是 MTR 发给他的窗口。

## 只有客户端时能拿到什么

在别人的服务器上（服务器没装问道），客户端手里只有 MTR 发给它的那一份：MTR 只把玩家附近大约 192 格的
铁路发下来，并且**每次更新都把客户端手里那套轨道整批换掉**——它是一个跟着玩家移动的窗口，不是只增不减
的数据。同步半径是 MTR 服务端的常量，客户端没有任何请求能把它放大。

问道自己的整图读数只在客户端主持这个世界时成立（单人、局域网：MTR 的模拟就在同一个进程里）；
服务端 → 客户端的同步只编进 1.20.6–1.21.1 两个加载器的节点，1.20.1 Fabric 上还没有这条传输层。
所以在别人的 1.20.1 服务器上，能用的只有这个窗口，以及下面这份记忆。

**会话内记忆**。`MtrKnown` 记住的是 MTR 发来的**原始轨道**，按 MTR 自己的轨道 id 区分（4.x 是它给的
hex id，3.x 是问道按两端方块坐标与交通类型编的 `m3:` id），而不是记住由这些轨道推导出来的「每条线跑
哪几条轨」。`MtrTransit` 规划一条线路的车程时用的是**当前窗口的轨道 + 这次会话记住的轨道**，同一条
轨道以窗口那份为准。于是一条线相邻的两站只要先后各进过一次窗口，这一次就能从头规划到尾；以前只能
规划到最新那个窗口的边缘，地图上的线因此断成一截一截。

上限：一次会话最多记 20 000 条轨道、1 000 000 个顶点；没有名字的轨道、不足两个顶点的轨道不记；
到达上限之后**停止记忆**而不是忘掉最早的——忘掉最早的等于把已经画出来的线自己拆掉，日志里会有一条
警告。顶点上限同时也是落盘文件大小的上限。

**落盘**。记忆按世界 + 维度存成 JSON，与道路数据放在一起：`config/howtogo/<世界>/<维度>-mtr-rails.json`，
例如 `config/howtogo/某个服务器/minecraft_overworld-mtr-rails.json`。联机时「世界」这一层取的是服务器
地址，所以两台服务器的记忆不会串在一起。打开世界或切换维度时在客户端线程之外读入；写盘是防抖的
（记忆 5 秒不再增长才写），离开世界与切换维度时也写；写入先写 `.part` 再改名，中断只会留下旧文件或新
文件，不会是半个。文件本身是紧凑 JSON（不缩进）、坐标四舍五入到 3 位小数：它是缓存，读得回来就行，
缩进和小数位只会把它撑大几倍。换维度时旧的窗口被丢弃、改读那个维度自己的轨道，所以一个维度的铁路
不会被规划进另一个维度。

这个文件是**MTR 读数的缓存**，不是玩家写的数据：读不懂就改名成 `<文件名>.corrupt`，这一次从 MTR 新发
的窗口重新记；空记忆永远不会覆盖已存的文件。关掉 `mtr_transit` 只清掉内存里那份，文件不动；想彻底
重来把文件删掉即可。

它改善的是**连续与稳定**：走到的路网跨会话还在，线路跨窗口连起来，同一段轨道不会被一波更新抹掉。
它不能做的是**让没走到过的路网出现**——客户端这边没有绕开 MTR 同步半径的办法。要在别人的服务器上看到
整张路网，必须由服务器那一侧把数据给出来：服务器装本模组（MTR 服务端同步，1.20.6–1.21.1 两个加载器
都有；1.20.1 Fabric 仍缺这条传输层），或者装 MTR Map Overlay 的收集器。

## 换一个 MTR 版本后怎么证明还认

两条命令，一条核对名字、一条核对读取器本身，都不需要开游戏：

```powershell
.\tools\mtr3-probe\run.ps1          # 3.x：类/字段/方法逐条核对（真 1.20.1-Fabric classpath）
.\tools\mtr3-probe\bind.ps1         # 3.x：把真读取器编进去，用 MTR 自己的类跑一次完整转换
.\tools\routing-harness\run-fast.ps1 -MtrJar <jar>   # 4.x：反射握手检查
```

`run.ps1` 量的是**两套名字**：Fabric 节点自己的 classpath 用官方（Mojang）名字，运行中的 Fabric 游戏用
intermediary 名字（`net.minecraft.class_2338` 之类），所以它跑 dev 与 production 两遍，后者才是运行时真正
会命中的拼法。`bind.ps1` 用的是后者，并真的用 `Station`/`Platform`/`Route`/`Rail` 造一条铁路跑转换，
包括一条多轨道、含反向存储重复项的整图轨道 map（数量、两端坐标、高度、缓存复用都断言）。

结果记在 `tools/mtr3-probe/build/*.log`；`-MtrJar <path>` 可以指向别的 3.x 构建。官方 3.x 的包名
（`org.mtr.mod.*` / `org.mtr.*`）由同一张候选表覆盖，但没有 jar 可核对时不会假装验证过。
